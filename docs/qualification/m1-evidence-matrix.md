# M1 evidence and acceptance matrix

Status: working traceability ledger, 2026-07-22. This document separates what exists in source from
what has been observed on hardware or proved in a deployed system. It complements the
[M1 system contract](../specs/m1-system-contract.md) and the [execution roadmap](../roadmap.md); it
does not weaken either one.

## Evidence vocabulary

Every requirement advances through distinct evidence classes. A later class does not exist merely
because an earlier class is green.

| Class | Meaning |
| --- | --- |
| `S` source | The boundary, implementation, or procedure exists and builds or parses. |
| `L` local executable | Deterministic unit, integration, simulation, or fault tests pass locally. |
| `H` hardware | The named behavior was observed on the owned sealed Omi and Android handset. |
| `D` deployed | The production-like cloud application or live Astrale instance passed the named test. |
| `E` end to end | One correlated owned-device run crossed every named boundary with failure evidence. |

States are `proved`, `prepared`, `partial`, and `open`. `Prepared` means the next procedure and its
guardrails exist; it is not a successful observation. Evidence that may contain identity, media, or
credentials remains under ignored `local/` storage. Tracked artifacts contain only redacted facts and
digests.

## Promotion rule

An M1 release candidate is eligible only when every row required by Gates 0–7 has its named `H`, `D`,
or `E` evidence and no row relies solely on `S/L` where physical or deployed behavior is claimed. A
waiver must name the requirement, risk owner, expiry, containment, and why the user-visible promise is
still truthful; a waiver cannot redefine M1 completion.
